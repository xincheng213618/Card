## 1. 人物是初始模板，技能是组合数据

```text
模式规则 ── 创建/初始化 ── 人物运行时
人物模板 ── 默认值 ────────┘
                          ├─ 当前属性与资源
                          ├─ 技能实例及其获得来源
                          ├─ 装备、标记与有期限的效果
                          └─ 阶段/回合/整局使用记录

技能定义 ── 触发绑定 + 条件 + 代价 + 选择 + 效果步骤
基础模组 ── 实现这些节点类型，供所有技能组合复用
```

人物模板只提供名字、立绘、默认性别/势力/体力上限及默认技能 ID。创建牌局时，模式据此生成运行时实例；之后规则读取当前有效状态，不通过人物名字推断技能或属性。

体力是可改变的资源；体力上限、性别、势力等有初始值和明确的运行时修改机制。不同属性需要各自的冲突、期限和归一化策略，不能都当作无类型的字符串字典。降低体力上限是否同时调整当前体力等行为，由该基础操作和模式规则明确决定。

默认技能、对局中获得的技能、装备授予的技能、临时技能都使用技能实例。保留 `SkillId + BindingId + OwnerSeat + SkillInstanceId`，并增加或复用明确的授予来源与期限。移除一个来源不应错误移除另一个来源授予的同一技能；同名多来源是叠加还是合并，由技能定义/模式的叠加政策决定。

角色属性变化、技能获得/失去/失效都通过受控操作提交，同时维护订阅和查询缓存。技能失效不等于删除定义；当前暂停中的技能是否继续，按该绑定的继续策略处理。定义对象不可变，牌局状态不保存在定义或反射创建的 handler 中。

用户给出的[单骑无双攻略](https://club.sanguosha.com/thread-1366189-1-1.html)描述了对局中购买技能和战法的组合玩法。本设计借用“同一角色动态获得不同能力”作为架构验收场景，不在本次实现商店、货币或整个活动模式，也不将旧攻略数据视为当前规则权威。

## 2. 两条公共规则链路

### 2.1 规则时机 → 触发器 → 组合执行

主流程只发布明确的规则时机，例如回合开始、阶段开始/结束、用牌目标确定前后、伤害前后、进入濒死、牌移动完成。每个时机有稳定的上下文、来源和窗口身份。`AfterDamageApplied` 与整个伤害结算结束不是同一个时机，不能用含糊的 `AfterDamage` 同时表示两者。

当前 `MatchSkillBindingIndex` 已按席位把有效技能绑定投影为不可变 shard：生命周期与数值查询保留 `SkillId + SkillInstanceId` 实例语义，主动技、贡献、view-as、强制牌身份及旧卡牌／判定窗口保留按 `SkillId` 去重的既有语义。shard 只缓存定义、节点、来源和绑定身份，不缓存 HP、手牌、装备、条件结果、目标、限次或已暂停候选；技能授权 revision 或国战主副将选择／显隐变化时仅惰性重建对应席位。窗口仍冻结候选身份；真正发动、支付或恢复前按当前状态复验拥有关系、目标／支付资格和实时规则查询，但触发级条件继续读取该窗口首次冻结的 facts，不因索引刷新重采样或增补候选。不能让反射类型顺序决定规则顺序。

候选由技能实例/绑定标识，不依赖 `SkillKind` 或人物名。一次伤害触发还是每点伤害触发必须显式建模；同一玩家需要选择技能先后时，调度器发出通用排序选择，不能用字母排序代替玩家决策。

规则窗口属于结算执行过程，和用于 UI/日志的事后通知分开。不要订阅所有审计事件后递归修改牌局：这会模糊“修改伤害前的机会”和“伤害已生效”的边界。重入通过数据帧/任务栈和父子关系处理。

### 2.2 规则查询 → 修正器 → 有效值或合法性

持续效果按需查询，不人为制造触发事件。现有 `SkillRuleQuery`、`SkillProgramModifier`、`SkillProgramRules` 是演进基础，查询的上下文还需按能力补充目标、卡牌动作来源及阶段身份。

| 规则项 | 应表达的含义 |
| --- | --- |
| 攻击范围 `AttackRange` | 模式默认范围、武器范围与技能修正；和座位距离分开 |
| 角色间距离 `Distance(source,target)` | 存活座位基础距离及来源/目标方向修正；可能不对称 |
| 特定牌距离限制 | 只影响该牌/来源的距离校验；距离豁免不能绕过目标禁令 |
| 出杀次数上限 `SlashUseLimit` | 当前规定作用域允许使用的次数；上限和“已用次数账本”分开 |
| 是否计入次数 | 这一次用牌是否消费额度；和“上限增加”分开 |
| 摸牌数、手牌上限 | 模式基础值、人物当前状态、技能/装备/临时修正的组合 |
| 目标合法性、可响应/可抵消 | 独立布尔/集合规则，不把所有限制折成一个数值 |

模式提供默认规则，装备、技能和战法提供带来源及期限的修正。每一种查询明确“基础值、覆盖、加减、上下界、禁止/授权”的组合政策；冲突覆盖依规则处理或拒绝歧义，不能依注册顺序覆盖。无上限是显式值，旧 `int.MaxValue` 适配逐步退出，不传播到加减运算。

`LegalActions`、实际命令提交、AI 和 UI 解释必须消费同一查询结果。必要时返回来源明细，用于解释为什么可出牌、为何距离不足或次数用尽。

## 3. 小模组接口，而非一人物/一技能一类

已有 `SkillProgram` 继续作为规则定义，已有 JSON 与展示文件分离。C# 的接口实现对象应主要是基础能力处理器：摸牌、回复、失去体力、移动一组牌、选择子集、判定、拼点、插入阶段等。

建议职责分为：

| 部件 | 输入与输出 | 不拥有的职责 |
| --- | --- | --- |
| `SkillProgramCatalog` | 校验/编译组合定义与 gameplay hash | 牌局可变状态、人物专属代码 |
| `SkillProgramEffectCatalog` | 节点类型 → handler，启动时注册 | 按技能 ID 选择实现、牌局中的重复反射 |
| `TriggerDispatcher` | 规则窗口/当前技能实例 → 有序候选 | 执行人物专属分支 |
| `SkillProgramExecutor` | 编译计划/数据帧 → 推进、等待选择或子结算、完成 | 直接持有整个 `GameEngine` 或可写玩家对象 |
| `SelectionRuntime` | 候选、数量/聚合约束、可见性 → 合法选择及校验 | 识别“称象”等技能名 |
| `RuleQueryService` | 查询上下文/修正来源 → 有效值或约束 | 决定 UI 布局、消耗使用次数 |
| 核心宿主能力 | 原子牌移动、伤害/回复/濒死、阶段调度 | 技能文案、技能组合条件 |
| `GameEngine` | 命令入口、牌局协调、公共能力适配 | 逐技能的询问、条件、AI 和 Resume 分支 |

接口采用窄的只读查询和受控效果能力。不能用包含所有私有字段/方法的 `IGameEngine` 替换具体引擎引用；也不能把大段人物实现搬到更多 `partial GameEngine` 文件后声称职责已解耦。

基础 handler 允许反射发现：只扫描明确指定的代码程序集，启动时一次发现公共具体实现，按类型稳定排序并校验重复节点类型/版本/构造要求。运行时使用冻结注册表，不按类名字符串调用方法，不反射访问引擎私有成员。JSON 只能引用已支持的能力；缺少 handler 在加载/启动阶段报明确错误，不能运行到一半才静默跳过。

节点参数、继续策略、限次政策和基础执行语义必须进入兼容性判定。内容图语义进入 gameplay hash；代码 handler 的语义变化按运行时能力版本/规则版本管理，不把程序集枚举顺序当指纹。已有定义和动作身份持续保留，不重新生成随机技能实例 ID 破坏回放。

## 4. 三个迁移样例决定缺少哪些基础类型

以下是语义流程；三个样例已在 schema 11 组合定义中实现，表格不是可直接加载的 JSON。

| 技能 | 组合声明 | 需要补齐的公共能力 |
| --- | --- | --- |
| 当先 | 有效回合开始 → 强制插入额外出牌阶段 → 正常回合继续 | 明确回合窗口、阶段调度/插入、阶段身份与限次重置 |
| 伏枥 | 自己进入濒死 → 可选发动 → 消费整局一次额度 → 查询现存势力数 → 回复至目标体力 → 翻面 | 濒死自救绑定、聚合数值表达式、回复至数值、翻面；复用已有整局状态仓 |
| 称象 | 自己受到伤害的规定窗口 → 可选发动 → 亮出顶四张 → 选择点数和≤13的子集 → 获得所选 → 弃置补集 | 伤害窗口绑定、公开临时牌集、受约束子集选择、命名牌集及补集移动 |

例如称象不是一个 `ChengxiangHandler`，而是 `RevealTopCards(4)`、`SelectCardSubset(sum(rank) <= 13)`、`MoveBoundCards(selected, owner.hand)`、`MoveBoundCards(revealed - selected, discard)` 的组合。同一选择能力换候选来源、数量或约束就能供其他技能复用。

基础选择必须给候选规模设明确边界，不能无限枚举所有子集。称象四张牌可以枚举至多 16 个选项，规模更大的选择沿用服务端约束提交与通用 UI。数据帧保存牌集、选择结果、执行游标、父帧与待决策身份，禁止保存闭包/Task/UI 对象。

保留每个样例原有真实语义：空牌堆可正常结束；弃牌仅清理本技能拥有的临时牌；未发动不亮牌；公开牌与私人选择分开；阶段插入后正确恢复；濒死成功恢复原父流程；先推进执行游标再挂起子结算，避免重复付费。

## 5. 属性与拥有关系的迁移边界

当前 `PlayerRuntime` 已有可变 `Hp/MaxHp` 和动态 `AcquiredSkillIds`，不能宣称它们全部写死。主要欠缺在于状态仍集中于引擎私有类，部分规则直接读取 `player.General.Gender`，多个技能仍按 legacy kind 路由。

迁移时把人物模板、当前人物状态、技能拥有/失效状态、回合作用域状态分开。先提供统一的有效属性/有效技能查询，再逐项替换旧直接读取。所有赋予、移除和到期操作必须能由命令前缀重建，不在 UI 上单独修改属性。

必须验证“模板没有改变，角色获得技能后立即能触发；失去或失效后不再收集；恢复后按规则生效”。临时改变性别或体力上限的效果也通过同样的当前值查询被目标规则看到。是否实现某一具体变性/变更体力技能由内容迭代决定，本架构不凭空增加游戏规则。

## 6. 实施顺序与分工

具体批次和当前写权见 [存量技能迁移计划](SKILL_MIGRATION_PLAN.md)。由现有“持续迭代”任务负责整合、架构任务独立验收；用户已明确允许使用 `gpt-5.6-sol` 子智能体并行实施独立模块及已交接目录，不使用其他模型子智能体。

当前第一步的范围由用户明确限定为 **GameEngine、人物与技能解耦**。先交付独立人物状态/技能持有集、基础执行器与窄宿主接口，再以当先、伏枥、称象的实际迁移验证边界；距离、次数等查询层保留后续收敛安排，不在这一步扩展新玩法。

1. **先抽执行器**：把已有主动组合程序的条件、游标、暂停/恢复和基础效果分派抽到独立运行时；通过 handler 接口及反射注册五种已存在基础效果。保留原 JSON、事件顺序和命令前缀语义，用真实现有程序验证。
2. **统一触发候选**：在现有 `Triggers` 与程序触发帧基础上改用稳定技能/绑定身份，补齐回合、阶段、伤害和濒死窗口。先明确各窗口位置与次序，再替换 legacy 收集链。
3. **补选择/阶段/数值节点并迁移样例**：当先、伏枥、称象成为组合定义，删除其专属决策/AI/公开投影/恢复分支。保留规则行为测试，测试不再要求专属枚举和私有字段。
4. **收敛规则查询与人物状态**：把默认值、装备、技能、临时效果纳入同一查询契约；把当前属性读取与模板解耦，验证动态获得/移除/失效及多个来源。
5. **按机制批量迁移并恢复内容扩展**：已覆盖基础能力的新技能仅维护组合数据、展示和自身行为场景。缺能力则先补一个复用节点，不复制人物专属流程。

持续迭代任务承担独立运行时/基础 handler 与后续组合迁移；架构任务负责接口裁决、宿主接入及整合验收，二者按文件明确写权。门禁任务只读审查时不同时改产品文件。现有用牌限制 A 切片保留，随后作为组合节点接入；暂不创建 `QiaoshuiModule` 人物类或继续扩张按武将 partial 的实现路线。

`PhaseSkillModules`、共享拼点和结果取牌已经验证的能力继续复用，它们是公共机制资产。其 C# 内容模块属于过渡消费者；逐步由同一程序执行器调用这些能力，避免长期维持两套条件、限次、选择和恢复语义。

## 7. 验收标准

- 对已有能力，新增技能只需新增/修改组合定义、展示和必要场景；无需在引擎、AI、WPF 中增加技能名字或枚举分支。
- 基础运行时可用窄的假宿主独立测试，不需要构造完整 `GameEngine` 才能验证顺序、条件、暂停和代价失效。
- 当先、伏枥、称象完成迁移后，相应专属规则函数真正删除；仅换文件或包接口不算通过。
- 同一组基础节点至少由多个技能消费；不得把完整称象逻辑塞进名为“通用”的单一节点。
- 同一角色使用默认技能及后来获得的技能走同一触发/查询链；属性变更、技能失效和到期均即时生效且可重放。
- 默认距离/范围/次数与装备、技能、临时修正组合后，人类合法动作、提交、AI 与 UI 结果一致；有明确作用域和冲突政策。
- 所有新暂停点验证玩家权限、私有数据、过期/伪造输入、牌区守恒、父流程恢复和当前 Replay。基础保障在机制层共享，内容场景只补自己的差异。
- 局部迭代用定向测试，公共切片完成后集中全量验证。未迁移部分明确标注，不能以单个切片通过宣称整个引擎已经解耦。

不以修改文件少或删除测试多作为提速指标。用“相同流程是否重复实现、内容能否独立组合、缺失能力是否只补一次、测试反馈能否局部获得”判断改造价值。
