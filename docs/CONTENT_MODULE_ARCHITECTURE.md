# 内容模块与规则引擎的职责边界

2026-09-21。当前落地范围是阶段技能模块试点，不代表所有技能已经迁移。

## 问题与目标

新增一个武将的主要成本来自职责交叉：内容逻辑需要知道引擎的私有 pending 字段、阶段续接、AI 轮询、WPF 提示枚举和公共状态断言。拆成 `GameEngine.<武将>.cs` 仍共享同一个类，不能隔离这些职责。

本次审计时，`GameEngine.cs` 约 2.9 万行，GameEngine 文件共 37 个；最近六个内容提交分别涉及 15、24、23、21、24、26 个文件。文件数只是症状。真正的验收标准是：内容作者能独立理解、实现、调试一个技能；只有缺少可复用规则机制时才需要扩展引擎。

## 目标分工

| 组件 | 拥有的职责 | 不应承担的职责 |
| --- | --- | --- |
| 内容模块 | 规则条件、效果组合、名称说明、版本来源、可选策略 | 直接改 GameEngine 私有状态、决定父流程怎么恢复 |
| 技能运行时 | 触发候选与次序、技能实例、限次、询问、执行游标 | 按武将名字分配另一条专用结算路径 |
| 核心规则能力 | 牌移动、用牌、伤害、判定、濒死、死亡、阶段推进 | 持有每个内容技能的文案和条件 |
| 玩家投影与 WPF | 私有提示、选项呈现、提交命令、表现 | 从描述推断规则、自己决定可选目标 |
| AI | 从合法选择中决策；必要时消费内容模块提供的策略 | 另一套技能效果或合法性规则 |
| 测试场景 | 明确初始牌局、提交命令、验证结果和暂停恢复 | 为了碰到技能条件反复搜索随机种子 |

现有 ContentRegistry、稳定 SkillId、命令校验、CardZoneStore、ResolutionFrame、SkillRuntimeStateStore 和私有快照继续作为基础。现有 JSON SkillProgram 保留；C# 内容模块先作为有明确能力边界的另一种实现，不为每个新规则先开发一套 JSON 语法。

## 已落地的纵向试点

入口契约在 `src/CardGame.Core/PhaseSkillModules.cs`：

- `IPhaseSkillModule` 是无状态内容实现，只接收冻结的 `PhaseSkillContext`。
- `CreatePlan` 返回声明式 `SkillActivationPlan`。本版仅支持可选发动/跳过和有界摸牌效果。
- `PhaseSkillFrame` 保存技能 ID、绑定、实例、时机、冻结上下文、计划和执行游标。帧没有模块对象、闭包、Task 或 UI 对象。
- `GameEngine.PhaseSkills.cs` 是宿主适配器：获取引擎事实、验证并冻结计划、通过原牌区能力执行效果、恢复原阶段。
- `PendingDecision.SkillPrompt` 给 UI 技能身份、标题和说明；已有 `Choices`、`PromptId`、Revision 和玩家脱敏路径保持权威。

内容实现放在 `src/CardGame.Content.Standard/Skills/`：

- `JingceModule`：出牌阶段结束，用牌数达到体力值时可摸两张。
- `BiyueModule`：结束阶段可摸一张。

两者共用候选调度、私有询问、人类/AI 回答、摸牌、限次和阶段续接。旧 DecisionKind、choice action 和精策事件只作为已有客户端/测试的兼容投影保留；新模块可以直接使用 `DecisionKind.SkillModule`，无需新建技能枚举或引擎分支。

此版本只有自己的阶段边界，要求当时结算栈为空；不支持跨拥有者触发、付费选牌、嵌套伤害/判定/死亡、任意脚本。不能因为有 InstructionIndex 就声称已实现这些能力。已有 JSON 程序还没有迁入同一个执行器。

## 新增内容的实际路径

1. 明确武将版本和技能规则，先找已有能力能否表达。
2. 对本版支持的阶段技能，在 Content 的 Skills 下实现无状态模块，注册到 `ContentSkillDefinition.PhaseSkill`。可复用已有两个真实模块。
3. 模块只描述条件与效果；禁止接收整个 GameEngine、可写玩家对象或完整对手手牌。
4. 用固定场景验证发动、跳过、条件不足、伪造/过期回答、私有视图、AI 和当前 Checkpoint/Replay。
5. 缺少机制时，先由架构层定义新的时机/选择/效果契约及恢复规则，再由内容实现消费它。不要为这个武将复制一份 pending/Resume/AI/WPF 分支。

## 后续拆分顺序

1. **统一选择契约**：在现有有限 choices 上扩展选牌、选目标、组合限制与私有槽位，UI 按交互类型呈现。保持“用户选择”和“核心重新校验”分离。
2. **用牌生命周期**：将单目标、多目标、转化来源和用牌次数记录收敛到一个拥有明确父子关系的 CardUse 上下文。龙吟作为第一个复杂消费者，防止次数回退重复执行。
3. **共享触发与子结算**：统一候选顺序、失效重检、代价提交和子帧完成后的续接。此后逐步让 JSON 和 C# 模块调用同一能力执行器。
4. **迁移内容**：按同类机制迁移，逐步删除专属 pending 字段与路由；历史代码只保留尚未迁移的适配路径。
5. **内容清单和开发工具**：从模块清单生成当前武将池、素材索引和测试发现；编写固定场景构造器，再增加按模块/机制选择测试的入口。

每一步用第二个真实技能检验抽象是否可复用。公共文件改动可以合理存在，不能用文件数量代替规则正确性或可理解性。

## 兼容与验证

模块 SkillId、Revision、Window 和运行时契约版本进入内容指纹。C# 方法体不自动参与哈希，改变模块行为必须提升模块 Revision；改变同一内容指纹下的核心回放语义仍按 `DEVELOPMENT_GATES.md` 调整全局规则版本。开发期旧存档不做静默迁移。

新模块的独立测试使用无 LegacyKind 的两个合成内容模块，验证不用专属枚举/AI 分支也能顺序询问、保护私密信息、拒绝伪造与过期回答、精确摸牌并重放。真实精策/闭月继续验证既有规则路径，WPF 测试检查实际提示按钮和恢复。

测试不得捕获一个历史异常后把整条混合测试算作 PASS：异常后的当前断言没有执行。当前行为与退役历史子场景必须分离，统计分别报告 passed/failed/skipped。

协调约定：架构任务负责接口、核心运行时和最终整合；内容任务仅按已确定契约接 UI 与场景；测试任务负责明确的历史测试拆分。共享工作区中同一产品文件只有一个修改者，最终构建集中执行。既有 staged/未提交工作保持原样，不因本轮重构自动提交。
