# 内容模块与规则引擎的职责边界

2026-09-26 当前指令：按公共能力整批删除旧接口和执行链，不维护历史包指纹、旧版本注册树或兼容投影。当前玩法由统一执行路径及行为测试保证，开发期间仅编译和定向检查，整批合并后统一验证。下文历史验收记录不构成继续保留旧实现的要求；本轮进度与边界见 [技能边界整批迁移](SKILL_BOUNDARY_MIGRATION.md)。

2026-09-22 更新：目标架构以 [组合式规则引擎](COMPOSABLE_RULE_ENGINE.md) 为准。人物持有属性和技能实例，技能由基础节点组合；反射用于注册基础 handler，不以每个技能新增 C# 类作为默认开发方式。下文记录已落地的阶段技能与共享拼点过渡切片，不代表整体迁移已经完成。

## 问题与目标

新增一个武将的主要成本来自职责交叉：内容逻辑需要知道引擎的私有 pending 字段、阶段续接、AI 轮询、WPF 提示枚举和公共状态断言。拆成 `GameEngine.<武将>.cs` 仍共享同一个类，不能隔离这些职责。

本次审计时，`GameEngine.cs` 约 2.9 万行，GameEngine 文件共 37 个；最近六个内容提交分别涉及 15、24、23、21、24、26 个文件。文件数只是症状。真正的验收标准是：内容作者能独立理解、实现、调试一个技能；只有缺少可复用规则机制时才需要扩展引擎。

## 目标分工

| 组件 | 拥有的职责 | 不应承担的职责 |
| --- | --- | --- |
| 内容模块 | 规则条件、效果组合、名称说明、版本来源、可选策略 | 直接改 GameEngine 私有状态、决定父流程怎么恢复 |
| 技能运行时 | 触发候选与次序、技能实例、限次、询问、执行游标 | 按武将名字分配另一条专用结算路径 |
| 核心规则能力 | 牌移动、用牌、伤害、判定、濒死、死亡、阶段推进 | 持有每个内容技能的文案和条件 |
| 玩家投影与 WPF | 私有提示、选项呈现、提交命令、表现 | 从描述推断规则、自己决定可选目标 |
| AI | 从合法选择中决策；必要时消费内容模块提供的策略 | 另一套技能效果或合法性规则 |
| 测试场景 | 明确初始牌局、提交命令、验证结果和暂停恢复 | 为了碰到技能条件反复搜索随机种子 |

现有 ContentRegistry、稳定 SkillId、命令校验、CardZoneStore、ResolutionFrame、SkillRuntimeStateStore 和私有快照继续作为基础。现有 JSON SkillProgram 是组合定义的主干；缺少行为时扩充可复用基础类型和执行器。已经交付的 C# 内容模块作为过渡消费者保留，后续收敛到同一组公共能力，不另建一套人物 DSL 或长期重复运行时。

## 已落地的纵向试点

入口契约在 `src/CardGame.Core/PhaseSkillModules.cs`：

- `IPhaseSkillModule` 是无状态内容实现，只接收冻结的 `PhaseSkillContext`。
- `CreatePlan` 返回声明式 `SkillActivationPlan`，支持可选发动/跳过、有界摸牌及一次拼点子操作。
- `PhaseSkillFrame` 保存技能 ID、绑定、实例、时机、冻结上下文、计划和执行游标。帧没有模块对象、闭包、Task 或 UI 对象。
- `GameEngine.PhaseSkills.cs` 是宿主适配器：获取引擎事实、验证并冻结计划、通过原牌区能力执行效果、恢复原阶段。
- `PendingDecision.SkillPrompt` 给 UI 技能身份、标题和说明；已有 `Choices`、`PromptId`、Revision 和玩家脱敏路径保持权威。

内容实现放在 `src/CardGame.Content.Standard/Skills/`：

- `JingceModule`：出牌阶段结束，用牌数达到体力值时可摸两张。
- `BiyueModule`：结束阶段可摸一张。

两者共用候选调度、私有询问、人类/AI 回答、摸牌、限次和阶段续接。旧 DecisionKind、choice action 和精策事件只作为已有客户端/测试的兼容投影保留；新模块可以直接使用 `DecisionKind.SkillModule`，无需新建技能枚举或引擎分支。

阶段入口只有自己的阶段边界，要求进入时结算栈为空。共享拼点允许双方在其结果窗口消费模块；其他跨拥有者触发、任意付费选牌、嵌套伤害/判定/死亡与任意脚本仍未统一。已有 JSON 程序还没有迁入同一个执行器。

## 第二条纵向切片：共享拼点与结果取牌

简雍审计分为两个机制阶段。第一阶段已提供拼点/结果取牌；巧说的下一张合格牌目标增减与失败禁锦囊尚未实现，简雍没有注册进正式武将池。

规则以[一将成名官网经典页](https://x.sanguosha.com/hero/314.html)和[2016 年官方说明](https://www.sanguosha.com/news/20161102_6141_0912)为本次版本来源；[当前 OL 页面](https://www.sanguosha.com/hero/178)存在不同文案，不能混用。纵适使用稳定 ID `classic:jianyong-zongshi`，与刘表已有的 `classic:zongshi`（宗室）区分，拼音相同不等于同一技能。

- `PhaseSkillWindow.PlayStarting` 在进入出牌阶段且重置阶段限次后触发。跳过出牌阶段不会触发；当先的每个实际出牌阶段各自触发。
- `BeginSkillPindian` 是阶段模块声明的子操作。宿主发布自己的手牌与其他非空手牌角色的组合选项，再私下询问对手。双方确认前不公开发起者选牌。
- `PindianFrame` 保存父帧、参与者、阶段、实体 ID、公开结果、候选索引与冻结取牌计划；不保存回调或模块对象。父 `PhaseSkillFrame` 在启动子帧前前移游标，恢复后只执行剩余效果。
- `IPindianResultModule` 只接收参与者的公开拼点结果和仍在本次处理区的牌 ID。`PindianCardClaimPlan` 只能可选取得其中一张牌。模块按当前回合角色起的座次及稳定 SkillId 顺序询问，逐项重检技能与牌的可用性；同点对双方都不是赢。
- 公共结果窗口展示本次仍在处理区的实体牌，取牌提示只给拥有者。完成后只弃置未被取得的牌，再恢复原父流程。
- 天义、陷阵、驱虎已使用该共享操作；各自只保留发动条件与结果效果。旧 DecisionKind/action 和 `PindianResolvedEvent` 是兼容投影，共用 SkillPrompt、AnswerPrompt、AI 选择与帧续接。
- `Skills/ZongshiModule.cs` 是真实内容消费者，以测试场景接入；它没有专属 Core pending、AI 分支或 WPF 路由。正式武将注册待巧说及交互覆盖完整后进行。

当前拼点能力只支持一个干净的阶段/主动技能父帧，不支持任意深度嵌套。烈刃仍有伤害后的独立拼点路径，下一轮必须接入，才能保证简雍作为烈刃对手时的纵适。结果模块目前只支持取得实体拼点牌，没有点数修正、拼点替换或结果触发中的伤害。

`AdvanceAfterHumanCommands=false` 时，阶段开始技能完成后恢复 `Phase=Play`、栈空；下一次 `AdvanceOneStep` 建立普通 `PlayCard` 提示。这是宿主推进职责，内容模块不得自己恢复阶段。

此次共享操作改变既有拼点技能的帧、PromptId、事件序列和暂停点，规则版本提升为 v115，避开已经退役的 v102–v114。Checkpoint 仍是已接受命令前缀回放；帧可序列化测试不意味着已经支持整栈直接加载。模块 Revision 仍负责本地内容语义指纹。

## 巧说剩余的用牌设计问题

现有 `BeginCardUse` 直接冻结目标并发出 `TargetsConfirmedEvent`，各牌种先各自决定目标；`CardUseTargetsFinalized` 是目标已确定后的程序窗口，不能当成通用增减目标入口。杀的多目标还由旧方天画戟上下文续接，借刀带有武器持有者与被杀角色的目标组合，无中生有/酒等使用空目标列表表达自身效果。这些差异需要先统一，不能只改 `CardUseFrame.TargetSeats`。

下一阶段先定义使用中的有效牌种、实体来源、初始目标、合法额外目标、删除后下限、复合目标槽位及逐目标效果，再接“一次性下一张合格牌”的回合状态。必须测试转化牌、群体牌、借刀、距离豁免与其他目标禁令、下一张牌即使不增减也消耗、失败后锦囊使用与响应边界、回合清理与 Replay。规则版本固定为所选经典规则，不能混入当前 OL 页面变体。

具体接口、牌种适配、提交顺序和验收矩阵见 [用牌生命周期实现契约](CARD_USE_LIFECYCLE_DESIGN.md)。该文档描述待实现能力，不能作为其已经完成的证明。

## 新增内容的实际路径

1. 明确武将版本和技能规则，先找已有能力能否表达。
2. 对本版支持的阶段技能，在 Content 的 Skills 下实现无状态模块，注册到 `ContentSkillDefinition.PhaseSkill`。可复用已有两个真实模块。
3. 模块只描述条件与效果；禁止接收整个 GameEngine、可写玩家对象或完整对手手牌。
4. 用固定场景验证内容自身的发动、跳过、条件与特有交互。伪造/过期回答、私有视图、AI 和当前 Checkpoint/Replay 的共同保障复用机制级测试；只有新交互或新恢复边界才扩展相应检查，不为每个武将重复一套模板。
5. 缺少机制时，按既定职责增加可复用的时机/选择/效果契约及恢复规则，先验证再消费。执行任务可以独立完成边界内的扩展；只有需要改变身份、隐私或结算契约时才请求架构裁决。不要为这个武将复制一份 pending/Resume/AI/WPF 分支。

## 后续拆分顺序

1. **统一选择契约**：在现有有限 choices 上扩展选牌、选目标、组合限制与私有槽位，UI 按交互类型呈现。保持“用户选择”和“核心重新校验”分离。
2. **用牌生命周期**：将单目标、多目标、转化来源和用牌次数记录收敛到一个拥有明确父子关系的 CardUse 上下文。龙吟作为第一个复杂消费者，防止次数回退重复执行。
3. **共享触发与子结算**：统一候选顺序、失效重检、代价提交和子帧完成后的续接。此后逐步让 JSON 和 C# 模块调用同一能力执行器。
4. **迁移内容**：按同类机制迁移，逐步删除专属 pending 字段与路由；历史代码只保留尚未迁移的适配路径。
5. **内容清单和开发工具**：从模块清单生成当前武将池、素材索引和测试发现；编写固定场景构造器，再增加按模块/机制选择测试的入口。

每一步用第二个真实技能检验抽象是否可复用。公共文件改动可以合理存在，不能用文件数量代替规则正确性或可理解性。

## 兼容与验证

模块 SkillId、Revision、Window 和运行时契约版本进入内容指纹。C# 方法体不自动参与哈希，改变模块行为必须提升模块 Revision；改变同一内容指纹下的核心回放语义仍按 `DEVELOPMENT_GATES.md` 调整全局规则版本。开发期旧存档不做静默迁移。

新模块的独立测试使用无 LegacyKind 的两个合成内容模块，验证不用专属枚举/AI 分支也能顺序询问、保护私密信息、拒绝伪造与过期回答、精确摸牌并重放。真实精策/闭月继续验证既有规则路径，WPF 测试检查实际提示按钮和恢复。

测试不得捕获一个历史异常后把整条混合测试算作 PASS：异常后的当前断言没有执行。当前行为与退役历史子场景必须分离，统计分别报告 passed/failed/skipped。

协调约定：架构任务负责职责边界、契约与关键机制验收，必要时亲自完成有边界的架构改造；持续迭代任务负责契约范围内的 Core 能力实现、内容、UI、测试与后续自主开发，不再把每个武将的实现队列反向交给架构任务。门禁任务按明确范围检查验证流程。共享工作区中同一产品文件只有一个修改者，读审任务不同时修改，最终构建集中执行。已验收能力内的新增内容无需逐项等待架构批准。既有 staged/未提交工作保持原样，不因本轮重构自动提交。
