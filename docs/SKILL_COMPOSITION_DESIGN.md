## 1. 要达到的结果

新增技能时，通常只提交技能规则配置、独立的展示描述和场景用例。只要已注册的基础能力足够，就不修改 GameEngine，不增加 SkillKind，不增加专属 Prompt 类型，也不修改 WPF 的技能分支。

只有出现现有能力无法表达的规则行为时，才扩展一个可复用的底层能力，并为这个能力补测试。复杂技能仍可以由多个触发器、查询修正和牌转换规则组合而成，不要求“一技能等于一个效果”。

技能描述供人阅读；规则定义供引擎执行。两者通过稳定的技能 ID 关联，不能从中文描述推断或执行规则。

配套文件：

- [规则配置示例](content/skill-composition/skills.example.json)：展示基础技能、龙胆／冲阵、雷击／鬼道、武魂的组合方式。
- [独立中文描述](content/skill-composition/zh-CN.example.json)：只负责名字、说明和提示文案。
- [BWIKI 概念与协作边界](content/skill-composition/BWIKI_RULE_ALIGNMENT.md)：资料版本、标签与执行语义、下一批通用机制和内容任务分工。

这些旧 JSON 是完整设计契约的示例，当前加载器不会解析它们。示例中的 example 命名空间不会进入正式选将池；基础能力名称也不代表当前已经实现。可运行内容位于 `src/CardGame.Content.Standard/SkillPrograms/`：体验内容由独立的 `standard-composed-skills` 包注册，已验收的正式武将程序也可由自己的版本化内容包注册。

## 2. 当前实现的依据与边界

| 当前入口 | 已有能力 | 本次需要补齐的部分 |
| --- | --- | --- |
| [ContentSkillDefinition](../src/CardGame.Core/ContentRegistry.cs) | ID、描述、LegacyKind 映射 | 独立规则图、能力依赖和版本；拒绝无实现的技能绑定 |
| [IPassiveSkill / IActiveSkill](../src/CardGame.Core/Skills.cs) | 摸牌数、距离、杀次数查询；固定主动技能效果模板 | 可配置条件、数值表达式、基础动作和步骤组合 |
| [CompositePassiveRules](../src/CardGame.Core/GameEngine.NationalSkills.cs) | 多个已编写技能的查询叠加 | 同一个新技能可组合多个基础能力 |
| [ResolutionFrame](../src/CardGame.Core/Resolution.cs) | 判定、伤害、濒死、死亡、询问的可检查帧 | 通用技能帧、程序游标、子帧续接和明确的时机窗口 |
| [Triggers](../src/CardGame.Core/Triggers.cs) | 伤害和判定候选的稳定排序 | 跨规则时机的统一收集、失效重检和同一时机排序策略 |
| [Events](../src/CardGame.Core/Events.cs) | 提交后的可信宿主观测事件 | 执行期间的规则上下文；转化来源、因果关系和角色身份 |
| [CardZoneStore](../src/CardGame.Core/CardZones.cs) | 实体牌位置和批量移动 | 通过受控能力复用，不允许配置直接改牌区 |
| [GameReplay](../src/CardGame.Core/Replay.cs) | 按规则版本重放已接受命令前缀 | 新规则图指纹及执行器版本；保留旧路径 |

几个具体问题决定了重构方向：

1. GameEngine 中仍有大量技能专用的 pending 状态及续接函数。现有雷击依附于成功打出闪后的 AttackResolution；“自己使用闪电后判定”不能仅靠换描述获得支持。
2. 这项历史缺口已由 v2 的 `CardActionContext`、精确 `CardConversionSource` 和已接受响应窗口补齐：冲阵不靠“最终牌是杀／闪”识别，普通赵云与 SP 赵云的技能实例也不会混用。v3 已增加改判完成后的最终判定结果窗口；v4 已增加改判前的通用替换能力；v5 已允许最终结果绑定选取目标并进入统一伤害、濒死和死亡流程。由精确牌动作发起新的自身判定仍需下一版本扩展。
3. v4 将旧判定牌进入弃牌堆或技能拥有者手牌做成显式政策，并以替换提交时相对判定主体冻结的判定牌有效花色／点数过滤后续摸牌或回复；候选牌资格则按技能拥有者持有时检查，既有鬼才／鬼道路径和旧存档行为不被反向修改。
4. 现有死亡函数连续执行死亡、弃牌、奖惩和胜负检查；武魂需要明确的死亡技能窗口、已死拥有者资格及嵌套死亡处理。
5. EventCommitted 在提交后向观察者发布，不能直接拿它做会修改状态的技能订阅总线。规则触发和界面通知必须保持不同的职责。

## 3. 分成四层

| 层 | 内容 | 新技能通常是否修改 |
| --- | --- | --- |
| 展示层 | 名字、完整描述、提示语、本地化、图标、语音键 | 增加数据 |
| 技能定义层 | 触发条件、代价、目标、步骤、修正器、转化规则、限次、标记 | 增加数据 |
| 规则执行层 | 候选排序、选择、表达式求值、步骤推进、暂停恢复、身份与版本校验 | 不修改 |
| 基础规则层 | 摸牌、移动牌、伤害、回复、判定、改判、用牌、死亡等 | 缺少新能力时才扩展 |

执行过程：事件到达规定时机 → 收集技能候选 → 决定顺序 → 检查条件 → 询问与选择 → 支付代价 → 执行效果步骤 → 等待必要子结算 → 返回原流程。

被动数值修正、牌转换是纯查询，不经过会改变状态的触发效果路径。

可选增摸的例子使用摸牌阶段中已经开始的 DrawCountCalculating 结算窗口，给本次待摸牌操作增加临时修正。它可以暂停询问，但不等于任意一次“查询摸牌数”都会弹框；UI 预览、AI 评估和合法性检查调用的查询始终无副作用。

## 4. 内容定义与能力注册

### 4.1 技能规则定义

每个 SkillDefinition 包含以下相互独立的部分：

- id、revision、rulesetId、sourceRefs：稳定身份、规则修订、所属规则集、核对来源。
- triggers：一个或多个触发绑定；各自声明时机、条件、可选性、拥有者资格、粒度和效果。
- activations：主动入口；声明阶段、限次、选择、代价和效果。
- modifiers：摸牌数、手牌上限、距离、杀次数等纯规则查询修正。
- viewAs：实体牌筛选、有效牌型、使用／打出上下文和转化来源。
- stateDefinitions：标记、回合计数、限定次数等状态的类型、作用域和清理规则。

展示文件用相同 id 保存 name、description、prompt 文案。展示更新不决定执行逻辑。说明可以引用公开参数以减少数值漂移，但复杂规则仍保留人工编写的完整描述，不声称能自动证明文案与规则等价。

技能的**标签**、**执行形态**与**交互入口**必须分开建模。主公技、锁定技、限定技、觉醒技、转换技属于技能标签；状态技与触发技描述的是技能部分如何持续生效或在时机到达后发动；`Active` 只表示本应用存在由玩家主动选择的动作入口。锁定技标签本身不等于“必定发动”，也不获得额外结算优先级；觉醒技则同时带有锁定与限定语义。后续完整规则图应使用独立的 `tags`、状态定义、触发绑定和 `activations` 表达这些含义，不能把它们折叠成一个互斥 `SkillKind`，也不能从展示描述反向推导。

当前 D5 元数据层已经提供结构化标签、状态／触发形态和主动操作入口；纯查询修正仍由规则自动应用，`activations` 由玩家主动选择。标签与入口只描述已实现语义，不代替对应的使用账本、初始状态、切换／重置和可见性契约。

### 4.2 编译和校验

装载时先把 JSON 编译成不可变的类型化规则图，而不是在每次发动时解析字符串。

编译器检查：ID／节点 ID 唯一、引用存在、能力及语义版本可用、参数类型、事件字段可访问性、变量定义与分支作用域、效果输出类型、限次与标记作用域、规则集依赖。任何失败都拒绝加载并报告技能 ID 和节点路径。

未注册能力、未知枚举值或缺少执行器不能回退成 None。旧 LegacyKind 仅在旧内容适配器中存在；新技能直接用 SkillId，不要求增加编译期枚举。

条件和数值采用受限表达式树，例如 eq、and、in、gte、add、count、maxBy、markCount；不允许随意访问 CLR 对象、执行字符串代码或访问随机源。候选查询返回类型化的玩家／牌／标记集合。

### 4.3 基础能力契约

每个能力注册：OpId、SemanticVersion、输入／输出类型、允许调用的上下文、是否改变状态、是否可暂停、失败策略、可见性、审计信息和最低规则集要求。

能力处理器只能通过受控的规则服务更改游戏状态。它不能获得可任意修改的 PlayerRuntime 或集合；所有实体牌转移仍走 CardZoneStore 的验证与账本。

优先提供：

| 类别 | 基础能力 |
| --- | --- |
| 牌与体力 | draw、discard、give、obtain、damage、loseHp、recover |
| 选择 | choosePlayer、chooseOwnCards、chooseTargetCard、chooseOption、reorder |
| 判定 | judge、replaceJudgment、readFinalJudgment、claimJudgmentCard |
| 出牌 | useVirtualCard、respondWithCard、viewAs；都进入正式用牌／响应流程 |
| 状态 | addMark、removeMark、clearMark、recordUsage、grantSkill、invalidateSkill |
| 生命周期 | enterDying、causeDeath；直接死亡与伤害分别建模 |
| 控制 | sequence、if、switch、foreachSnapshot、repeatBounded、stop |

give 是牌移动语义，recover 是回复语义；不再为每个组合增加 GiveCardsAndRecover、GiveCardsAndSlash 之类枚举。

## 5. 时机和上下文必须先定义清楚

### 5.1 内部规则窗口

RuleWindow 是引擎内部的执行入口，RuleEventContext 是该窗口的不可变事实及受控引用。IGameEvent 继续是提交后的输出。不能在 EventCommitted 回调中发动技能，也不能靠日志反向驱动引擎。

第一批窗口至少包含：

| 窗口 | 用途 |
| --- | --- |
| DrawCountCalculating / HandLimitCalculating | 摸牌数和手牌上限修正 |
| CardUseDeclared / CardUseTargetsFinalized | 用牌已成立、最终目标已确定；冲阵等需要区分这两个阶段 |
| CardResponseAccepted | 使用／打出响应牌已成立，原响应效果尚未继续 |
| DamageCalculating / DamageCommittedBeforeDying / AfterDamage | 改伤害、记录实际伤害及前置状态、伤害后技能；时序由规则集定义 |
| JudgmentReplacing / JudgmentFinalized / JudgmentCleaningUp | 改判、最终结果、判定牌收尾 |
| DyingStarted / DeathCommitted / DeathCleaningUp | 濒死救援、死亡技能、死亡清理 |
| CardsMoved / PhaseStarting / TurnEnded | 失去装备、失去最后手牌、阶段技、状态清理 |

表中 `CardUseTargetsFinalized`、`CardResponseAccepted`、受限的 `JudgmentReplacing` 与 `JudgmentFinalized` 已分别由 v2／v4／v3 提供，其余名称仍是拟议契约。武魂的标记必须计入致死伤害，不能等“只收集存活者”的普通伤害后窗口；具体绑定窗口必须跟所选规则版本一致。

### 5.2 保留牌的来历和参与者

CardActionContext 至少保存 actionId、parentActionId、physicalCardIds、effectiveKind／suit／rank、conversionChain、actorSeat、providerSeat、requesterSeat、responderSeat、opponentSeat、currentTargets 和 use／response 上下文。

- conversionChain 记录明确的 SkillInstanceId 和转化步骤，不从颜色或最终牌型猜测。
- actor、提供实体牌的人、技能拥有者和伤害来源可以不同；护驾、激将必须保留这些区别。
- 冲阵的对方由当前用牌或对抗响应定义；不能总是取伤害来源，也不能固定为当前回合角色。
- 牌的实体数据不被转化覆盖。有效花色与原花色分别提供，红颜、武神等使用哪一种由能力契约明确。
- 同一实体牌存在多种合法转化方式时，合法动作明确携带选中的转化路径。

同一张响应牌可能在外部日志中既被描述为“使用”又被描述为“响应”，内部只能产生一次对应的规范化接受时机。响应动作统一进入 CardResponseAccepted，不再为同一个动作额外发布独立用牌的 CardUseDeclared。真正由该响应触发的新用牌拥有新 ActionId。

CardUseTargetsFinalized 保留最终目标集合；需要“对方”语义的绑定按规则集展开为逐目标的 TargetOccurrence，并提供 opponent 与 occurrenceId。冲阵在允许多目标的规则集中是逐目标还是整体一次，必须由该版本的绑定政策决定，不能只取 targets[0]。示例采用逐最终目标政策。

### 5.3 触发排序和重检

候选键使用 WindowId、SkillInstanceId、BindingId、OccurrenceIndex；同一技能内的多个绑定也保持独立身份。订阅多个相关窗口的绑定还可声明按 CardActionId／TargetOccurrence 去重，以免把同一响应重复算作使用和打出。合法的后续事件可以再次触发，不能使用“本次根结算触发过”这种过宽去重。

规则集决定优先层、行动顺序和同一玩家同时触发技能是否需要选择顺序。稳定 ID 只用于规则允许的平局收敛，不替代应交给玩家的选择。

窗口建立时冻结候选身份与事件事实；发动前重检技能是否仍有效、所需角色是否仍存在；支付前重检牌归属和选择合法性。已经支付的效果是否在拥有者死亡／失去技能后继续，由绑定的 continuationPolicy 决定。

伤害触发区分 oncePerDamage 与 eachDamagePoint。后者保留每点的出现序号和独立选择；只有在语义等价且没有逐点观察者时，执行器才能优化合并。

## 6. 通用执行帧、代价与选择

SkillExecutionFrame 保存 ProgramId／ProgramHash、SkillInstanceId、BindingId、WindowId、InstructionPointer、类型化局部变量、子帧引用、限次预留和 CostCommit 状态。嵌套技能各自持有帧，逐步替代单个 _pendingLeiji 等全局槽位。

一个效果返回 Continue、AwaitChoice、AwaitChild、Completed、Cancelled 或 RuleError。选择、判定、伤害、濒死都是可等待的子过程；父帧只在子过程明确完成后推进一次。帧中不存闭包、委托、WPF 对象或 Task。

代价分三步：确认完整合法选择 → 原子提交该批代价 → 等待代价触发的子结算完成。失去体力作为代价仍会进入濒死；苦肉获救后才能摸牌，死亡后按该技能的继续策略结束。后续目标失效通常不返还已支付代价。

整个技能可能跨多个用户命令，不能把它伪装成一次可回滚的大事务。保证每次已接受命令和基础操作的状态一致；程序错误进入可诊断的失败状态，不能清空栈并假装结算成功。

每个节点声明目标失效／空集合策略，例如 skip、stopBinding、chooseAgain。满血回复是合法的零回复，不应自动取消随后伤害。手牌不存在时的获得动作是零张，不凭空生成牌。

选择继续使用 PromptId、Revision、稳定 ChoiceId 和服务器端合法性验证。对方暗牌只呈现不透明选择令牌；配置、UI 和 AI 均不能通过候选字段取得牌面。执行器在宿主内把令牌解析为真实实体牌。

foreachSnapshot 固定遍历集合但逐次检查成员状态；有意重复的规则使用明确的重复节点和退出条件。调度预算只暂停并报告异常循环，不静默截断合法效果或吞掉剩余伤害。

## 7. 数值修正、标记和限次

修正器采用每种查询明确的计算契约：基础值 → 固定值覆盖 → 加减修正 → 上下界约束。存在同层覆盖冲突时，由该查询的规则政策决定优先级或在加载时拒绝歧义。无上限使用符号 Unlimited，不依赖 int.MaxValue 的算术。

杀的使用次数上限、是否计入次数、距离限制、能否响应、能否抵消是不同规则项；不能用一个“无限杀”标记同时代表全部。

标记由 MarkStore 管理，键包含 MarkDefinitionId、持有者及可选来源技能实例。定义必须声明整数／布尔／集合类型、公开性、共享或按来源分隔、重置时机和清理策略。

梦魇的公开表现是同名标记合计，rules v91 起可信账本按技能拥有者座位保存来源分桶，死亡候选和清理只读取当前拥有者的分桶。其他版本若要求真正共享或按技能实例进一步细分，必须显式选择不同作用域；不能因为实现方便而悄悄改变多人拥有同名技能时的语义。

使用次数由 UsageLedger 管理，支持每阶段、每回合、每轮、整局、每目标以及每事件次数。记录点可为代价提交或指定成功结果，配置必须明确。限定技、觉醒技和普通主动技共用状态基础，但各自的触发与显示不同。

## 8. 用用户给出的复杂技能检验设计

### 8.1 神关羽：武魂／梦魇

本节以受伤后增加梦魇的版本检验机制。BWIKI 当前页面还含造成伤害后增加梦魇的版本；正式配置须固定来源 revision 和版本，不能把本节示例作为所有版本的技能描述。

拆成两个绑定，共用一个标记定义：

1. 伤害已经确定发生、致死处理开始前，按实际受到的伤害为有效来源增加梦魇。无来源、被防止的伤害和单纯失去体力按规则条件排除；致死伤害必须计数。
2. 进入允许死亡技能执行的窗口，即使拥有者已死亡，也保留其技能身份。筛出该拥有者来源分桶中梦魇最多的其他存活角色；并列时由拥有者选择；令所选角色判定，开放普通改判窗口；结果不满足桃／桃园结义条件时执行 causeDeath，再只清理该拥有者来源的标记。

causeDeath 不生成 Damage 或普通濒死救援。它保留技能原因与责任信息，进入统一死亡清理和模式奖惩政策，不能用“造成 999 点伤害”模拟。

rules v90～v92 已用合成武魂消费者覆盖致死前逐点标记、全零／最大并列、已死玩家私有 Prompt、普通改判、来源清理、胜负短路和两层嵌套；rules v93／schema 9 又把判定后的直接死亡提升为通用 `causeDeath` 效果，覆盖无伤害／无濒死／无击杀奖惩、嵌套死亡技能恢复和终局短路。rules v94／schema 10 进一步把武神拆成强制手牌身份 `cardIdentities` 与来源限定的 `slashDistanceLimit`，受控场景已冻结物理／有效身份、跨距离和通常次数边界。rules v95 已把神武将开局选择魏／蜀／吴／群建模为亮将前的独立私有设置状态，标签、印刷势力和本局有效势力互不代替；A53b2 已在经典包 1.67.0 完成两项技能和整将注册，C21 已完成肖像与 WPF 验收。零标记不选目标及结算后清标记参考了 QSanguosha 的该版本实现，但不能据此推断所有官方版本相同。

胜负检查是模式规则的显式时点。不能在可执行的死亡技能链中提前结束游戏，也不能一概要求“所有死亡技能永远先于胜负”。某模式若规定在更早时点结束，则必须终止后续窗口；武魂在该模式的可用性由规则集和场景测试确认。

### 8.2 张角：雷击／鬼道

普通张角和界张角必须分配不同的规则定义。当前官网普通张角是出闪后令其他角色判定；官网界张角包含自己出闪／使用闪电后判定，以及自己判定后的效果，两者的判定主体和目标选择时机不同。

界张角示例拆成：

- 绑定 A：自己使用／打出闪，或使用闪电 → 可选发动 → 自己进行一次判定。
- 绑定 B：自己的判定最终确定 → 黑桃则可选角色造成 2 点雷电伤害；梅花先回复自己 1 点体力，再可选角色造成 1 点雷电伤害。
- 鬼道：其他或自己判定牌生效前 → 选择符合黑色条件的自有牌 → replaceJudgment → 按所选版本决定旧牌去向 → 满足额外花色／点数条件时摸牌。

绑定 B 在 schema 5 中继续拆为结果互斥的稳定触发绑定：梅花回复是强制绑定，黑桃伤害和梅花伤害分别是可选选目标绑定。`optional` 只控制所在绑定，不能把梅花回复和伤害包进同一个总询问。绑定 A 已由 schema 6 的直接有效牌型过滤与 `startJudgment` 实现；它与绑定 B 仍是两个独立绑定。

黄天不属于张角本人点击的普通主动技。schema 7 把程序拥有者固定为当前存活且身份符合的主公，把入口 actor 固定为其他符合势力条件的当前出牌角色；牌名和花色过滤只读取 actor 自己的实体手牌。经典黄天配置为【闪】或【闪电】，界黄天配置为【闪】或黑桃，两者的使用账本都按 actor、技能拥有者和绑定记录，而不是消耗张角自己的主动技次数。

经典雷击与界雷击不能共用同一个“自己判定”动作。schema 8 让经典版本在【闪】动作接受后先用 `otherLiving` 选择判定主体，再以技能拥有者为判定发起者；最终订阅用 `subject:any + judgmentSource:owner + judgmentReasons` 只接回这条链，并以 `judgmentSubject` 对原判定主体结算伤害。界版本仍由 schema 6 令自己判定，再由 schema 5 在最终判定后另选伤害目标。

不能把绑定 B 限定成“由雷击 A 产生的判定”，否则八卦等其他判定与雷击的联动会漏掉。特定历史版本排除暴虐判定，应通过明确的 JudgmentReason 条件表达，不污染所有版本。

replaceJudgment 同时验证替换牌与当前判定牌，以一致的移动批次提交；不能先弃旧牌再发现新牌不可用。旧牌归弃牌堆或被获得是一个明确参数。配套 JSON 的交换版本为能力演示，不宣称是官网当前鬼道的完整规则。

该批次提交时也同步更新当前判定帧的牌引用，再开放失去装备等子触发；不能让子触发看到“牌已经移走、判定仍指向旧牌”的中间状态。改判的返回值冻结替换提交时所需的花色／点数，以免后续失去技能改变额外摸牌条件。

判定最终结果包含最终实体牌、有效牌型／花色／点数、判定主体、判定原因及因果来源；改判中间态不触发“判定后”。子技能结束后才恢复原判定收尾和原响应流程。

### 8.3 SP 赵云：龙胆／冲阵

龙胆只负责杀／闪互相转换并保留转化来源；冲阵独立订阅用牌目标最终确定或响应已成立的窗口，要求牌确实经对应龙胆实例转换，然后可选获得对方一张手牌。

这样普通赵云只绑定龙胆，SP 赵云绑定龙胆和冲阵。未来“某转换技能发动后摸牌”可以替换订阅条件和后续动作，不必复制龙胆代码。

冲阵发生在该牌效果继续之前，不应等待伤害成功；响应时的对方来自对抗上下文，南蛮／决斗／借刀等不能统一用 damage.source 代替。普通杀闪、八卦虚拟闪也不能因最终牌型相同而误触发。

## 9. UI、AI 与描述

WPF 根据通用 ActionDescriptor／PromptDescriptor 渲染：技能名、描述键、选牌区、数量、目标条件、可选按钮和完成状态。界面不通过 SkillKind 写新的发动分支；特殊交互只新增通用选择控件，例如牌序排序。

AI 消费与本人相同的过滤视图和合法选择，按效果语义、公开目标状态和明确策略提示评分。新技能必须先有可完成全部 Prompt 的通用策略；更好的专用策略是可选优化，不是让新技能生效的前提。

规则图和文案分别验证：编译器证明图可执行，参数占位校验防止文案缺字段，场景验证证明指定规则行为。仅有技能描述或技能登记成功不算实现验收。

## 10. 旧内容、存档和确定性

旧内容包、ContentHash、SkillKind 数值、旧命令格式和 RulesVersion 语义保持原样。旧保存按旧版本恢复，不能偷偷映射到新技能程序。

新路径增加可选的执行版本标识，具体版本号在实施时以最新代码为基线分配。新包显式选择 ProgramRuntime；兼容分派表保证同一窗口／技能实例只有一个执行后端，不能让旧分支与新绑定重复触发。

新规则指纹覆盖规范化规则图、表达式、参数、标记定义、能力语义版本、窗口／排序政策版本和规则集。已有 SHA-256 内容指纹只覆盖定义，不能证明任意 C# 执行器代码不变；底层语义修改必须提升相应版本并保留旧解释路径。

描述、翻译、语音单独记录 PresentationRevision；纯描述更新不改变新规则的 GameplayHash。旧 ContentHash 算法不因这次拆分而改变。若回放要求重现历史文案，再固定展示包版本。

第一阶段继续使用“种子＋版本＋已接受命令前缀”重建暂停点。通用帧设计为数据结构，不等于已经实现完整状态序列化；直接保存结算栈是另一项工作。

所有随机行为使用现有确定性随机源；所有候选排序、节点 ID、ChoiceId 和随机调用位置稳定。新主动命令可通过单独的 V2 命令携带 SkillId／BindingId／ActionId；旧 UseSkillCommand 保留适配，不强行扩大 SkillKind。

## 11. 分阶段实施与验收

| 阶段 | 交付 | 验收条件 |
| --- | --- | --- |
| 1. 定义与装载 | 类型化规则图、独立描述、能力注册、表达式校验、指纹 | 配置能加载；未知能力／错误类型／缺失引用被拒绝；改描述不改新规则指纹 |
| 2. 修正与转换 | DrawCount、HandLimit、SlashLimit、统一 ViewAs、CardActionContext | 英姿语义对应的可选增摸、咆哮、手牌上限、武圣、急救、龙胆可由配置表达；多技能不互相覆盖 |
| 3. 通用流程 | TriggerWindow、SkillExecutionFrame、选择、代价、状态和基础效果 | 苦肉、给牌回血、反馈及冲阵走同一执行器；支付后濒死与继续流程正确 |
| 4. 判定链 | 通用判定、改判、结果订阅、嵌套续接 | 迁移现有张角并保留当前语义，再用独立新定义接入界张角版本；改判和交换能暂停恢复 |
| 5. 死亡链 | 死亡拥有者资格、直接死亡、标记清理、模式胜负时点 | 武魂在明确规则集下通过致死计数、并列选择、改判、直接死亡和嵌套死亡场景 |
| 6. 逐批替换 | 现有技能迁移、通用 UI／AI 接入、减少专用状态 | 新内容不再进入技能名分支；旧回放 fixtures 仍通过；新暂停点可重放 |

阶段 2 的通用主动／响应选择描述必须同步接入客户端；每阶段都交付可实际运行的薄切片，不把所有交互工作留到最后。仅改文件组织、把 switch 搬到另一个文件不算完成重构。

先迁移现有可复用能力，再添加缺失能力。规则纠错和实现迁移分开：等价迁移用旧行为作为差分基线；修正规则用核对过的场景，并提升规则版本。

### 必须覆盖的测试矩阵

- 同一个武将同时具有增摸、手牌上限修正、无限杀、龙胆和冲阵；基础牌规则仍然有效。
- 一次受到两点伤害与两次受到一点伤害；失去体力、被防止伤害、无来源伤害、致死伤害分别验证。
- 使用／打出、自然牌／转换牌／无实体牌、单目标／多目标、目标被改动、提供者与使用者不同。
- 失去一血代价进入濒死，获救后只执行一次后续效果；未获救时不摸牌。
- 鬼道替换装备触发装备失去效果，再恢复原判定；连续改判只使用最终结果。
- 雷击梅花满血时仍能继续伤害；连环雷伤、反伤、死亡后父帧能正确推进。
- 武魂致死伤害增加标记、最高值并列、全零、判桃／桃园、被改判、直接死亡不进入普通救援。
- 玩家拒绝技能、目标手牌已空、技能途中失效、过期 Prompt、重复回答均不产生重复费用或效果。
- 每个新增可等待点保存并重放，事件顺序、牌区、标记、下一 Prompt 和确定性随机位置一致。
- 观察者异常不影响规则；AI／其他玩家快照不包含暗牌候选或规则图中的私有局部变量。

最终验收演示：只添加配置，组合“给牌后虚拟杀”“经指定转化后摸牌”“受伤给来源加标记，自己死亡时消费标记并判定”三个新技能，GameEngine、SkillKind、WPF 都没有新增技能专用代码。若基础能力不足，新增能力须命名为通用规则行为并由至少一个独立组合复用。
