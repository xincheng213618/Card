# 开发门禁边界

本项目把“内容指纹”和“引擎回放语义”分开管理，避免新增武将、技能或表现资源时反复抬高全局 `RulesVersion` 或内容包版本。

## 必须保留

- Checkpoint schema、当前规则版本、内容包签名和内容哈希必须全部精确匹配；不匹配的开发期存档直接判为过期。
- 同一内容包、同一内容哈希和同一命令前缀的解释发生变化时，统一提升当前规则版本并废弃旧开发存档，不维护迁移分支。
- 技能程序声明的最低引擎能力检查；旧规则不能执行它不理解的程序结构。
- 命令合法性、隐私、牌区守恒、原子性、帧续接和伪造输入防护。

## 不再作为门禁

- 仅新增武将、技能、卡牌、素材、说明或测试，不增加 `RulesVersion`。
- 未发布开发期不为每个武将递增内容包版本；Registry 内容哈希已经能让旧开发存档失效。只在形成明确的内容发布批次时调整包版本。
- 已由内容包版本和内容哈希隔离的功能，不再额外添加 `_rulesVersion >= N`。
- 不再为“旧规则版本 + 新内容包”补负向回归；真实旧存档必须携带并匹配它原来的包签名和内容哈希。
- 技能 JSON 的能力元数据可以先于全局规则版本解析；只有实际创建不满足最低能力的牌局时才拒绝。

## 规则版本何时可以增加

只有以下任一项成立时才增加：

1. 同一内容指纹下，既有命令的解释发生变化；
2. 事件顺序、结算帧、随机数消费或可恢复暂停点发生变化；
3. 当前开发存档需要明确失效，避免用旧命令前缀进入已经改变的结算路径。

新增内容时应验证内容哈希、正式玩法和当前 Checkpoint/Replay；不要同时制造内容包版本、全局规则版本两套逐项门槛。

## 开发期单项流程

新增普通武将或技能时默认只维护：内容定义、当前武将池、实际运行逻辑、针对性 Core 测试，以及确有 UI 变化时的 WPF 测试。不要逐项修改 `Replay.cs`、`SAVE_AND_RESUME.md`、`SKILL_COMPOSITION_DESIGN.md` 或追加旧版本对照分支。

迭代中用测试名称通用过滤器快速验证，例如 `--filter=Longyin`；同一批次完成后再运行一次完整 Core/WPF 回归和格式检查。内容包历史构造仅供现有历史测试，不要求新内容继续扩展历史版本矩阵。

## 已清理的历史范围

原 rules v102–v114 都只是给 `standard-classic-generals` 1.80.0–1.92.0 的内容增量重复设门禁，现统一回收到最后一个真实引擎语义版本 v101。项目尚未发布，因此不迁移或规范化任何其他版本的开发存档：新存档写 v101，恢复时也只接受 v101；版本不同应删除旧开发存档并重新开局。

第二轮按重要性把 Core 中显式的运行时版本判断从 126 个减至 63 个：移除了经典技能逐项启用、神势力选择、武魂目标选择和仁德的重复版本判断，保留核心结算顺序、序列化结构、技能程序能力、国战结构及事件账本边界。旧规则版本测试只作为历史记录，不再阻断开发；当前玩法与当前版本 Replay、内容包签名及内容哈希仍严格验证。
