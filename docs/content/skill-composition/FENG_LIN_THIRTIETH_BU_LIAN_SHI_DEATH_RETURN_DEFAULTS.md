# Engineering defaults, not an official FAQ

The published current OL text and original beneficiary selection stay unchanged. This followup changes the death replay recipe's operation to 6800 and therefore its content fingerprint; it leaves legacy 6303 unchanged.

- The original dead owner's Death/Dying and original attack remain in place. Only the already-dead victim's exact proven original Dying is filtered from active resolution while the new owning benefit program exists. Its parent window, candidate index, responder cursor, attempted bindings, turn and original attack identity are frozen and attested by one scalar fact hash.
- Actual Draw3 movement, short-deck actual counts, beneficiary gain observers and actual Recover1/replacement observers drain before the next instruction. Source death is expected in OwnerDied. Original skill instance and issuance are retained; the beneficiary cannot be substituted. A dead beneficiary cancels the remaining unpaid instruction, retaining already-issued cards and facts. Winner cancellation finishes paid descendants and the typed return.
- A normal configured damage observer may start real nested damage after the exact original benefit's movement/recovery. Damage preserves current source, amount, nature, redirection and chain propagation through the mature producer. The added admission requires the real paid subtree, not any ancestor with a receipt.
- New HP-loss Dying, actual damage Dying, DyingEntering, SelfDyingResponse, physical/multi-material response Peach and existing bound/zero-entity Alcohol use preserve their actual actors, providers, materials and typed return. The old original Dying is restored to active visibility when the owning root is popped, without rewriting it.
- A second live victim's Dying while another live rescue target is still pending remains rejected by the existing engine. The new filter does not hide live victims. This draft does not promise new arbitrary card-use entry points or a generalized concurrent-Dying scheduler.
- Four existing methods and registrations remain; only the existing original-beneficiary death method gains two small fixed-seed scenarios. The first issues real gain Damage -> DyingEntering -> recovery; the second issues real benefit recovery -> LoseHp2 -> DyingEntering -> real two-material Peach -> actual HP observer. Both preserve the true original Damage/Dying/Death and resume the cold-restored engine at each meaningful pause. Other legacy assertions stay intact.

Static-only delivery. No compiler, production loader, test, native AI run, benchmark or HTTP request was executed. The real commands/native response choice are future regression drafts, not runtime evidence.
