# Card development guidance

- Use PowerShell on this Windows workspace. Before a recursive delete or move, resolve and verify the absolute target, then use `-LiteralPath`.
- Ordinary new generals and skills that use existing capabilities change their content and registration. Existing shared loader, registry, and mechanism checks cover pure configuration. Add a focused behavior check only for behavior that is not already covered or for a bug fix; do not require a duplicate definition snapshot for each character. Do not raise the global rules epoch, skill JSON schema, or content package version per character. The content hash already distinguishes content changes during development.
- Raise `GameCheckpoint.CurrentRulesVersion` only when the same content fingerprint would replay commands differently. Raise `SkillProgramCatalog.RulesSchemaVersion` only for an incompatible rules JSON format; additive optional nodes can keep the existing schema. Change package versions for an intentional content release batch.
- Keep version sources in `src/CardGame.Core/Replay.cs`, `src/CardGame.Core/SkillPrograms.cs`, and the relevant package's `CurrentVersion`. Do not copy current numbers into unrelated tests or development guides.
- Add focused Core behavior checks for the new rule. Add WPF checks only for UI behavior, and shared mechanism checks when a shared capability changes. Reuse the existing `--filter=<name>` runners and `tools/Test-Changed.ps1`; do not add character-specific runner switches or a new test framework. Run the relevant checks during development and one appropriate full verification after a batch.
- Preserve checkpoint, replay, content fingerprint, input validation, privacy, and card movement boundaries. Do not delete historical compatibility code or change stored data solely to reduce test count.
